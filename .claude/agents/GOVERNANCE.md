# 에이전트 거버넌스 (운영 헌법) — 2026-07-28 제정, 같은 날 §8 증보

모든 에이전트는 업무 시작 시 이 문서를 Read한다. 지시서(개별 md)와 충돌하면 이 문서가 우선한다.

## 1. 자동 호출 원칙 (컨트롤 타워 의무)

- **본선(사용자와 대화하는 클로드) = 컨트롤 타워**다. 사용자가 에이전트 이름을 몰라도 된다 — 대화 내용이 어느 공정에 해당하면 본선이 **해당 에이전트를 자동 호출할 의무**가 있다(호출 안 하고 본선이 직접 처리하는 것은 편성 위반. 예외: 1분 내 끝나는 잡무).
- 연관 공정 자동 연결: 한 에이전트의 산출물이 다음 공정을 필요로 하면(예: 대본 완성→소재 요구서 발생) 본선이 **사용자 지시 없이도** 다음 에이전트에게 넘긴다. 단 외부 게시 실행·비용 발생·계정 생성은 항상 사용자 승인 게이트.
- 사용자 부재 시(클라우드 루틴·예약 작업)에도 동일 편성 적용 — 지시서가 저장소에 커밋돼 있으므로 클라우드 세션도 같은 팀으로 일한다.

## 2. 팀 구조 (3계층)

```
1층 컨트롤 타워: 본선 세션 (오케스트레이션·사용자 소통·대시보드 갱신)
2층 팀장 에이전트 12: 지시서(.claude/agents/*.md)를 가진 전담 책임자
3층 팀 내 하위 일꾼: 팀장 업무를 병렬 분할한 다수 일꾼
   — 구현: Workflow(워크플로 — 여러 일꾼을 병렬로 돌리는 지휘 스크립트)로 팀장 지시서를 상속한
     일꾼 N명을 동시 가동 (예: 소재 검증 10건 병렬, 채널 원고 7종 병렬 각색)
```

- **팀의 공유 기억** = 저장소 파일이다: refs/ 지식 베이스(팀 교과서), refs/asset-ledger.md(자산 대장), refs/agent-audit-log.md(감사 로그), refs/pipeline-status.md(상태판). 일꾼은 휘발되지만 파일은 남는다 — "기억은 파일로" 원칙.
- 에이전트 간 실시간 상호 대화(에이전트 팀 기능)는 아직 실험 단계 — 안정화 시 3층을 승격한다. 그때까지 팀 간 소통은 본선 경유 + "다른 팀 전달 메모"(산출물 끝에 첨부) 표준 양식.

## 4. 권한 · 책임 · 패널티

- **권한**: 각 에이전트는 주업무 범위의 실무 결정권을 가진다(지시서에 명시). 단 공통 상한: ①외부 게시 실행(§8 상시 승인 범위는 예외) ②비용 발생 ③계정 생성·인증 ④저장소 push는 본선·사용자 게이트를 거친다.
- **책임**: 각 지시서의 "품질 게이트"가 곧 책임 목록이다. 산출물에는 "확인한 것/못 한 것"을 명시할 책임이 있다 — 허위 "완료" 선언이 최중대 위반.
- **패널티(재발 방지 구조)** — AI 일꾼에게 벌점은 무의미하므로 다음 3단계로 구현:
  1. **위반 기록**: auditor가 refs/agent-audit-log.md에 건별 기록(에이전트·위반 유형·산출물·경위)
  2. **즉시 조치**: 산출물 반려·재작업(본선 집행)
  3. **누적 3회(동일 유형)**: 해당 지시서를 개정해 원인 자체를 제거하고, 가능하면 **훅(기계 강제 검사)으로 승격** — 같은 실수가 사람(사용자) 눈에 두 번 띄지 않게 하는 것이 목적
- **감사 독립성**: auditor는 제작 업무를 겸임하지 않는다(자기 산출물 감사 금지). 감사 통계는 marketing-analyst의 대시보드에 "품질" 축으로 반영된다.

## 5. 협업 프로토콜

- **인수인계 표준**: 산출물 + ①확인한 것/못 한 것 ②다음 공정에 필요한 입력 ③다른 팀 전달 메모(관할 밖 발견물) — 3종 첨부 의무.
- **자기충족 검증 금지(2026-07-30 발행 전 감사 적발 — rule9 정교화)**: 왕복 검증의 **기대값은 전송에 쓴 그 파일이면 안 된다.** 3편 쇼츠 설명란에 드라이런 잔재 `youtu.be/DRYRUNID`가 박혀 있었는데, 검증 스크립트가 전송 원본을 기대값으로 다시 읽어 "전문 일치"로 통과시켰다 — 원본이 오염되면 구조적으로 영원히 못 잡는다. 기대값은 **독립 근거**(대본·대장·실제 게시물·API 응답)에서 와야 하고, 전송 직전 **금지 문자열 가드**(DRYRUNID·BODY_URL·TODO·PLACEHOLDER)와 링크 생존 확인을 함께 건다.
- **완료 마커 파일 계약(2026-07-28 ops-analyst 진단 승격 — 신호 유실 3연발 재발 방지)**: 장시간 작업(렌더·검수·생산)을 맡은 에이전트는 완료 시 산출물 폴더에 `_DONE_<작업명>.txt`(완료 시각·산출물 목록 1줄씩)를 남긴다. 인수하는 쪽은 통지를 무기한 기다리지 말고 ①예상 소요 명시 ②대기 타이머 ③마커/산출물 파일 폴링의 3종 세트로 감시한다 — **완료 인수의 근거는 통지가 아니라 파일 실측이다**(rule7 확장).
- **우선순위 충돌 시**: 주업무 > 부업무, 발행 일정 임박 편 > 차기 편, 사고 대응 > 신규 제작. 판단 불가 시 본선에 에스컬레이션.
- **허가 창 최소화 수칙**: 조회 명령은 `cd 폴더 && git …` 복합형을 쓰지 말고 `git -C <경로> <조회명령>` 단독형으로 실행한다(복합형은 앱 안전장치가 사용자 허가 창을 띄움 — 자동 진행 원칙 위배). 자주 쓰는 읽기 전용 도구는 .claude/settings.json permissions.allow에 고정 등록돼 있다(저장소 동반 = 로컬·클라우드 동일 적용). 쓰기·삭제·게시·인터프리터 실행은 등록하지 않는다(안전선).
- **업그레이드 루프(살아있는 지시서)**: marketing-analyst의 분석·auditor의 감사·사용자 피드백 → 분기별(또는 사건 발생 시) 지시서·refs/ 개정 — 디자인 철학·톤앤매너·SEO 규칙은 고정물이 아니라 데이터로 진화하는 관리 대상이다.

## 6-2. 세션 인수인계 의무 (2026-07-30 사용자 지시 — 컨텍스트 소진 대비)

- **사용자 원문(2026-07-30)**: "컨텍스트 윈도우가 100%가 되기 전에 인수인계서 작성 후 세션을 마무리하고 다음 세션으로 넘어가는 것도 에이전트에 입력."
- **본선(컨트롤 타워) 의무**: 컨텍스트가 **약 80% 소진되면 즉시 인수인계서를 갱신**한다(100%를 기다리지 않는다 — 꽉 차면 쓸 여력이 없다). 갱신 대상 2곳:
  1. 장기 메모리 `~/.claude/projects/<프로젝트>/memory/session-handover.md`
  2. **저장소 사본 `refs/SESSION-HANDOVER.md`**(커밋·푸시) — 메모리에 접근 못 하는 세션(클라우드 루틴·다른 PC·다른 계정)도 같은 지점에서 이어받게 한다
- **인수인계서 필수 항목**: ①다음 세션 첫 할 일(진행 중 작업의 정확한 중단 지점·산출물 유무) ②완료분과 URL·커밋 ③이번 세션의 제도·규칙 변화 ④사용자 결정 기록(원문 인용) ⑤환경 실측(반복 사고 방지) ⑥미결 목록. **진행률의 원천은 항상 `refs/pipeline-status.md` + 실제 파일 실측**이라고 명기한다.
- **하위 에이전트 의무**: 장시간 과업 중 컨텍스트가 차면 스스로 종료 전에 **산출물·중단 지점·다음 단계를 파일로 남긴다**(§5 완료 마커 계약과 동일 원리 — "기억은 파일로"). 보고만 남기고 파일을 남기지 않는 종료는 위반.
- **세션 교체 시 인수 절차**: 새 세션·새 에이전트는 통지·전언이 아니라 **①인수인계서 ②상태판 ③실제 파일 실측** 3종으로 상태를 확정한다(전임 보고 무비판 승계 금지 — 3편에서 총감독 5대 교체 중 확립된 원칙).

- **자동 발행의 전제 조건(2026-07-29 감사 처방 — 이전엔 없어서 결함 5건이 사용자 눈에 먼저 닿았다)**:
  1. **산출물 스펙 실측 통과**(해상도·라우드니스·무음 비율·샘플레이트·프레임 이탈). 체크리스트의 모든 수치 항목은 "문서에 그렇게 적혀 있음"이 아니라 **"지금 파일을 재서 그 값이 나옴"으로만 통과 처리**한다.
  2. **발행 전 auditor 감사 1회**(유튜브 릴리스의 의뢰자는 release-director). 감사 미실시 상태의 자동 발행은 §8 범위 밖이다.
  3. 위 둘의 근거를 승인 행에 첨부한다. auditor는 사후 감사도 계속한다.
- **상시 승인에 포함되지 않는 것(항상 사용자 확인)**: 금전 결제·비용 발생 / 계정 생성·인증 / 게시물 삭제 / 채널 설정 변경 / 신규 플랫폼 최초 게시 / 품질 게이트 미통과 강행. ("결재"=업무 승인의 위임이며, "결제"=금전 지출은 위임 대상이 아니다.)
- **문제 발생 시**: 즉시 중단하고 사용자에게 한 줄 보고 + 필요한 최소 수동 조치(예: 파일 드래그 한 번)만 요청한다.
- **운영 모드**: release-director는 목표-루프(/loop) 방식으로 가동 가능 — 목표(예: "2편 발행") 달성 또는 차단까지 자율 반복.

## 9. 컨텍스트 예산 규율 (2026-07-30 신설 — "총감독 세대 교체"의 근본 처방)

**실측된 문제**: 총감독이 3편에서 5대까지 교체되고 매번 파일 실측으로 인수인계한 것은
"에이전트가 죽어서"가 아니었다. 전사 81건 기계 스캔 결과 —

| 실측 | 값 |
|---|---|
| 비정상 종료(크래시·타임아웃) | **0건**. 전사 5건 모두 마지막 이벤트가 정상 '최종 보고' |
| 컨텍스트 누적 | 총감독 411,015 / 감사관 384,240 / 음성 320,191 토큰. **압축 0회** |
| 그 누적의 정체 | 총감독 16.0MB 중 브라우저 도구 **11.7MB(73%)**, 음성 8.8MB 중 **89%**, 감사관 6.4MB 중 **70%** |
| 기본값 원흉 | `read_page` 반환 상한이 **기본 50,000자** — 한 번 호출로 컨텍스트를 크게 먹는 게 기본 설정 |
| 연속성 끊김 실물 | `"No agent named 'release-director' is reachable"` — **이름으로는 재연결 불가**, 그래서 새 세대를 스폰함 |

즉 원인은 두 개다: ①한 세대가 감당 못 할 양을 태운다 ②끝난 뒤 다시 못 부른다.
파일 실측 인수는 그 결과를 수습하는 임시방편이었다. 아래가 원인 자체에 대한 처방이다.

### 9-1. 무거운 도구는 위임한다 (컨텍스트 격리)
총감독·감사관처럼 **오래 살아야 하는 역할**은 브라우저 조종·긴 로그 판독·대용량 파일
통독을 **직접 하지 않는다**. 일회용 하위 에이전트에 맡기고 **요약만** 받는다.
하위 에이전트는 자기 컨텍스트를 태우고 사라지므로, 지휘자의 예산은 보존된다.
(쉬운 말: 사장이 창고 재고를 직접 세러 가면 하루가 다 간다 — 직원을 보내고 숫자만 받는다.)

### 9-2. 기계 강제 (훅)
- `.claude/hooks/context_guard.py` (**PreToolUse**) — 유입 차단: `read_page` 반환량을
  12,000자(명시 요청도 20,000자 상한)로 교정하고, `limit` 없는 120KB 초과 Read를 차단한다.
- `.claude/hooks/context_budget.py` (**PostToolUse**) — 예산계: 도구 결과 바이트를
  **에이전트별로** 누적(`agent_id` 키 — 서브에이전트 분리 계량 실측 확인)해 1.5MB/3.5MB/5.5MB에서
  당사자에게 직접 경보한다: 위임 권고 → 인계 준비 → 인계 후 종료.
  바이트는 토큰의 대리 지표다(정확 환산 아님 — 16.0MB↔411K, 6.4MB↔384K로 비례하지 않음).

### 9-3. 재연결 규율
총감독을 이어 쓸 때는 **새로 스폰하지 않고 SendMessage로 기존 세션에 이어 지시**한다.
이름(`release-director`)으로는 도달하지 않는다 — **스폰 시 받은 에이전트 ID로만** 재연결된다.
새로 스폰해야 하는 경우(ID 소실·컨텍스트 소진)에만 §6-2 인계 절차를 쓴다.
