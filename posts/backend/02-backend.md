## Part 1. 동적 웹의 탄생 — 서버가 "계산"을 시작하다

### [1991~] 정적 웹 서버 — 파일 배달부

- **문제(출발점)**: 웹 초기의 서버는 요청받은 HTML 파일을 그대로 돌려주는 파일 배달부였다. 누가 접속하든 똑같은 문서.
- **한계**: 방문자 수 카운터, 방명록, 검색 — "사람마다, 상황마다 다른 화면"이 불가능했다. A가 방명록에 글을 남겨도 B의 화면에는 나타나지 않는다 — 파일은 미리 만들어져 있고, 서버는 그 파일을 꺼내 줄 뿐이니까.
- **비유**: 자판기 — 버튼(URL)을 누르면 미리 만들어 둔 상품(HTML)이 나올 뿐, 즉석 조리는 못 한다.
- **출처**: CERN, "A short history of the Web" (home.cern) — 01편 Part 1 참조

### [1993] CGI — 서버 뒤에 요리사를 두다

- **문제**: 정적 파일만으로는 동적 콘텐츠(폼 처리, 카운터, 방명록)를 만들 수 없었다.
- **해결**: NCSA가 CGI(Common Gateway Interface — 서버와 외부 프로그램 사이의 표준 연결 규약) 고안. 웹 서버가 요청을 받으면 외부 프로그램(C, Perl 등)을 실행시키고, 그 출력(HTML)을 응답으로 돌려준다.
- **원리**: 파일을 "꺼내 주는" 게 아니라 매 요청마다 "새로 조립해서" 반환한다. 서버는 배달부 역할을 유지하되, 뒤에 즉석 요리사(프로그램)를 고용한 구조.
- **새로운 문제**: ① 요청 1건마다 프로세스(실행 중인 프로그램 한 벌)를 새로 생성 — 접속자가 늘면 서버가 프로세스 생성 비용으로 주저앉았다. ② 모든 기능을 바닥부터 직접 짜야 했다.
- **출처**: RFC 3875 (CGI 명세, 2004년 문서화); NCSA HTTPd 기록

### [1994] 쿠키 — 기억을 못 하는 HTTP에 붙인 메모지

- **문제**: HTTP는 무상태(stateless — 요청과 요청 사이를 기억하지 못하는 성질) 프로토콜이다. 로그인 상태 유지도, 장바구니도 불가능했다.
- **해결**: 넷스케이프의 23세 엔지니어 루 몬툴리(Lou Montulli)가 1994년 6월 쿠키를 고안 — 서버가 브라우저에 작은 데이터를 심어두고, 브라우저가 매 요청마다 그것을 자동으로 다시 제출하는 방식. 1994년 10월 13일 공개된 Mosaic Netscape 0.9beta부터 지원됐다.
- **디테일**: 개발 동기는 고객사 MCI가 요구한 **온라인 쇼핑 장바구니** 앱이었다. 이름은 포춘 쿠키(메시지가 안에 든 과자)에서 따왔다.
- **연쇄 예고**: 쿠키 → 세션 → JWT로 이어지는 "상태 관리의 역사"는 Part 3 말미에서 이어진다.
- **새로운 문제**: 사용자 추적 가능성 — 오늘날까지 이어지는 프라이버시 논쟁의 출발점. (구글은 2020년 서드파티 쿠키 퇴출을 선언했다가 2024년 7월 철회했다 — 30년 된 기술 하나를 못 빼는 이유는 그만큼 웹이 쿠키 위에 서 있기 때문.)
- **출처**: Lou Montulli 회고; Guinness World Records "First use of cookies"; RFC 2109 (1997, 쿠키 최초 표준)

### [1995~1999] PHP · ASP · Servlet/JSP — HTML 속에 코드를 심다

- **문제**: CGI는 동작했지만, ① 프로그램 전체를 짜야 해서 진입장벽이 높았고 ② 프로세스 비용이 컸다.
- **해결 1 [1995]**: 라스무스 러도프(Rasmus Lerdorf)가 PHP 공개 (1994년 작성, 1995년 6월 8일 공개. 원래 이름 Personal Home Page Tools — 자기 이력서 열람을 추적하던 개인 도구였다). HTML 문서 안에 코드 조각을 심으면 서버가 그 부분만 실행해서 채워주는 방식. 진입장벽이 극적으로 낮아졌다.
- **해결 2 [1996]**: Microsoft ASP (1996년 12월, IIS 3.0에 탑재) — 같은 문제의 MS 진영 해법.
- **해결 3 [1997~99]**: Sun의 Java Servlet(1997) / JSP(1999) — 프로세스 대신 JVM 안의 스레드(한 프로그램 안에서 일하는 여러 작업 흐름 — 새 프로그램을 통째로 켜는 것보다 훨씬 싸다)로 요청을 처리해 CGI의 프로세스 비용 문제를 해결. 기업 시장을 장악했다. JSP처럼 서버 쪽에서 화면을 완성해 내려주는 방식을 SSR(Server-Side Rendering — 서버가 화면을 만들어 줌)이라 부른다.
- **새로운 문제**: HTML(화면)과 비즈니스 로직(서비스의 핵심 규칙 — 계산·판정)이 한 파일에 뒤엉키는 스파게티 코드. 기능 하나를 고치려면 관련 없는 코드까지 다 봐야 했다. — 01편에서 HTML에 스타일이 섞여 CSS가 나온 것과 정확히 같은 구조의 문제가 서버 쪽에서 재현된 것.
- **곁가지 — 데이터는 어디에?**: 이 시절 사용자가 남긴 글은 서버 안 텍스트 파일에 순서대로 쌓였고, 특정 글 하나를 찾으려면 파일을 처음부터 끝까지 읽어야 했다. 이 문제의 해결(관계형 데이터베이스, MySQL, 쿼리)은 **→ 03 데이터베이스편**의 주인공이다.
- **출처**: php.net 공식 연혁; Java Servlet 1.0 명세 (1997); Wikipedia "Active Server Pages"

## Part 2. 구조화 — 프레임워크와 MVC의 시대

### [2004] Ruby on Rails — "설정보다 관습"

- **문제**: 웹 앱마다 반복되는 작업(DB 연결, URL 연결, 폼 처리)을 매번 처음부터 설정해야 했고, 스파게티 코드 문제는 여전했다.
- **해결**: 데이비드 하이네마이어 한슨(DHH)이 2004년 7월 Ruby on Rails 오픈소스 공개. 두 가지 원칙:
  - **MVC 패턴**: Model(데이터) · View(화면) · Controller(흐름 제어)의 강제 분리 — 스파게티의 구조적 해결
  - **Convention over Configuration(설정보다 관습)**: 정해진 규칙만 따르면 설정 없이 알아서 돌아간다
- **효과**: 2005년 브라질 FISL 콘퍼런스의 **"15분 만에 블로그 만들기" 데모**가 상징하듯 개발 속도의 혁명. 초기 트위터·깃허브·쇼피파이가 모두 Rails로 만들어졌다(트위터는 이후 대규모 트래픽 문제로 Scala/JVM 계열로 이전 — 이것도 "해결이 낳은 새 문제"의 사례다). Ruby 언어 자체가 "개발자가 즐거워야 한다"는 철학으로 만들어졌고, Rails는 그 철학의 웹 버전이었다.
- **형제들**: Spring 1.0 (2004.3, Java — 기업 시장), Django (2005.7, Python — 관리자 페이지 자동 생성), Express (2010, Node.js), Laravel (2011.6, PHP).
- **새로운 문제**: 프레임워크 모놀리스(한 덩어리 앱)는 편했지만, 트래픽과 팀이 커지면 배포·확장의 병목이 됐다 (→ Part 4).
- **출처**: rubyonrails.org 연혁; DHH "15-minute blog" 데모 (FISL, 2005); spring.io 릴리스 블로그 (2004.3.24); djangoproject.com 20주년 타임라인

### 📦 심화: MVC — 스파게티를 자르는 칼

```
사용자 요청
  → Controller : 요청 접수·흐름 제어 — "주문 받는 홀 매니저"
  → Model      : 데이터와 비즈니스 로직 — "주방"
  → View       : 결과를 화면으로 — "플레이팅"
```

- 01편의 HTML(구조)/CSS(표현)/JS(동작) 분리와 같은 철학 — **"섞이면 죽는다, 분리하면 산다"**는 소프트웨어 역사의 반복 패턴.
- 이때부터 웹 개발이 "파일 몇 개 짜기"에서 "구조를 갖춘 소프트웨어 공학"이 됐다.

## Part 3. API의 시대 — 서버, 화면을 버리고 데이터를 팔다

### [2000] REST — API의 문법을 정하다

- **문제**: 시스템 간 통신 방식이 제각각이었다. 당시 표준이던 SOAP/XML-RPC는 규약이 무겁고 복잡했다.
- **해결**: 로이 필딩(Roy Fielding — HTTP 1.1 명세의 주 저자)이 2000년 UC 어바인 박사논문에서 REST(Representational State Transfer) 제시.
- **원리**: 새 기술이 아니라 **HTTP를 원래 설계대로 쓰자는 원칙**. 자원(URL = 창구 주소, ENDPOINT) + 행위(GET 조회 / POST 생성 / PUT 수정 / DELETE 삭제)의 조합. 데이터를 다루는 기본 동작 묶음을 CRUDL(생성·조회·수정·삭제·목록)이라 부른다.
- **비유**: 식당의 표준 주문서 — 어느 식당(서버)이든 같은 양식으로 주문하면 알아듣는다.
- **현재**: Postman 조사(2025) 기준 API의 93%가 여전히 REST — 25년째 사실상 표준.
- **출처**: Roy Fielding, "Architectural Styles and the Design of Network-based Software Architectures" (UC Irvine 박사논문, 2000); Postman State of the API 2025

### [2002→2006] JSON — XML을 밀어낸 가벼움

- **문제**: 데이터 교환 표준이던 XML은 태그 중복으로 무겁고 파싱(기계가 읽어 해석하는 일)이 번거로웠다.
- **해결**: 더글러스 크록포드(Douglas Crockford)가 JSON(JavaScript Object Notation)을 발굴·표준화 — json.org 문서화 2002년, RFC 4627 표준화 2006년 7월.
- **원리**: JS의 객체 표기법(키&값 쌍)을 그대로 데이터 형식으로 사용 — 사람이 읽기 쉽고, 기계가 파싱하기 빠르고, JS와 궁합이 완벽.
- **의미**: REST + JSON 조합이 사실상의 웹 API 표준이 됐다.
- **출처**: Douglas Crockford, "The JSON Saga" 강연; RFC 4627 (2006)

### [2005] AJAX — 백엔드의 역할이 뒤집힌 순간

- **문제**: 데이터 하나를 갱신하려 해도 페이지 전체를 새로고침해야 했다.
- **해결**: 브라우저가 화면 뒤에서 몰래 서버와 통신하는 기법이 확산 (기술 자체는 이전부터 존재, 2005년 2월 제시 제임스 가렛이 AJAX로 명명. Google Maps·Gmail이 위력을 증명).
- **역사적 의미**: 이 순간부터 서버의 응답이 "완성된 HTML"에서 "데이터(JSON)"로 바뀌기 시작했다. 01편에서 본 SPA·프론트엔드 독립의 서버 쪽 반쪽이 바로 이것이다.
- **가속 [2007]**: 아이폰 등장. 모바일 앱은 HTML이 필요한 게 아니라 **데이터**가 필요했다 — 같은 서버가 웹과 앱 양쪽을 섬기려면 화면이 아니라 데이터를 줘야 한다.
- **결과**: 백엔드의 재정의 — **화면 제조기 → 데이터 공급자(API 창구)**. 화면은 프론트엔드(화면 제작자)의 책임이 됐다.
- **출처**: Jesse James Garrett, "Ajax: A New Approach to Web Applications" (Adaptive Path, 2005.2)

### [2015] GraphQL — REST의 빈틈을 찌르다

- **문제**: 모바일 시대에 REST의 두 가지 비효율이 드러났다 — 과잉 요청(필요 없는 필드까지 다 받음)과 과소 요청(화면 하나 그리는 데 API 여러 번 호출).
- **해결**: 페이스북이 GraphQL 공개 (2012 사내 개발, 2015 오픈소스) — 클라이언트가 필요한 데이터의 모양을 직접 질의하는 언어.
- **새로운 문제**: 캐싱·모니터링이 REST보다 복잡. REST를 대체하기보다 공존 중 (Postman 2025 기준 사용률 33% vs REST 93%).
- **출처**: graphql.org; Facebook Engineering 블로그 (2015.9)

### 📦 심화 1: 상태 관리의 연쇄 — 쿠키 → 세션 → JWT

로그인했는데 페이지를 옮기면 로그인이 풀린다? HTTP가 무상태(기억력 없음)라서 생기는 문제다. 30년에 걸친 해결의 연쇄:

| 단계 | 방식 | 해결한 문제 | 낳은 새 문제 |
|---|---|---|---|
| 쿠키 (1994) | 브라우저에 데이터 저장, 매 요청마다 자동 제출 | HTTP의 무상태 | 브라우저에 둔 데이터는 위변조 가능 |
| 세션 | 정보는 서버가 보관, 브라우저엔 **번호표**만 | 위변조 방지 | 서버가 여러 대면 번호표 관리 복잡 |
| JWT (RFC 7519, 2015.5) | 서명된 토큰에 정보를 담아 사용자가 소지 | 서버 무상태 복원 → 수평 확장 용이 | 발급한 토큰을 중간에 무효화하기 어려움 |

- **세션의 원리 — 은행 번호표**: 로그인하면 서버가 내 정보를 자기 메모리에 저장하고 **번호표(세션 ID)**를 발급한다. 다음 요청 때 번호표를 내밀면 서버가 "아, 3번 고객" 하고 알아본다. 번호표를 브라우저에 저장해뒀다가 자동으로 내미는 장치가 바로 쿠키다.
- **세션의 한계**: 정보가 서버 메모리에 있으니, 서버가 2대·10대로 늘어나면? 1번 서버에서 받은 번호표를 2번 서버는 모른다. 서버끼리 번호표 장부를 공유하는 관리 복잡성이 생긴다.
- **JWT(JSON Web Token)의 발상 전환**: 번호표를 버리고, **서버가 기억하는 대신 사용자가 증명서를 들고 다니게** 했다. 점(.)으로 구분된 세 부분 —
  1. **헤더**: 어떤 방식으로 서명했나
  2. **페이로드**: 실제 담긴 데이터 (내가 누구인지)
  3. **서명**: 위조 방지용 도장
- 비유: 공증 도장이 찍힌 통행증 — 내용이 증서에 다 적혀 있고, 도장(서명)만 검사하면 위조 여부를 알 수 있으니 **발급처(서버)가 아무것도 기억할 필요가 없다.** 어느 서버가 받아도 검증 가능 → 서버를 마음껏 늘릴 수 있다(→ Part 4 수평 확장).
- **주의 — Base64는 암호화가 아니다**: JWT의 세 부분은 Base64(어떤 데이터든 알파벳·숫자만으로 적는 표기법)로 인코딩될 뿐, 누구나 되돌려 읽을 수 있다. 위조를 막는 건 서명이고, 내용을 숨기는 게 아니다. 그래서 페이로드에 비밀번호 같은 민감 정보를 넣으면 안 된다.
- **패턴**: 상태를 어디에 둘 것인가(클라이언트 ↔ 서버)를 두고 30년째 진자 운동 중이다. 완벽한 답은 없고 트레이드오프(하나를 얻으면 하나를 내주는 교환)만 있다.
- **출처**: RFC 7519 (JSON Web Token, 2015.5); RFC 2109 (1997)

### 📦 심화 2: 인증·인가·해싱 — 보안은 선택이 아니라 전제

- **인증(Authentication)**: "당신은 누구인가?" — 로그인. 신분 확인.
- **인가(Authorization)**: "당신은 이걸 할 권한이 있는가?" — 로그인했다고 관리자 페이지에 들어갈 수 있는 건 아니다. 건물 출입(인증)과 서버실 출입 권한(인가)은 다른 문제.
- **비밀번호 해싱**: 비밀번호는 원문 그대로 저장하지 않고 해싱(단방향 변환 — 믹서기에 간 과일처럼 원상복구가 불가능하고, 같은 입력이면 항상 같은 결과가 나오는 계산)을 거쳐 저장한다. 로그인 때는 입력값을 다시 갈아서 결과끼리 비교한다. **핵심: DB가 통째로 해킹돼도 공격자는 원본 비밀번호를 알 수 없다.**
- **실제 사고가 증명한 것**: 2012년 링크드인 해킹 — 1억 1,700만 개 비밀번호가 유출됐는데, 낡은 방식(SHA-1)으로 소금(salt — 해싱 전에 섞는 무작위 값, 같은 비밀번호도 다른 결과가 나오게 함) 없이 저장돼 있어 72시간 만에 90%가 풀렸다. 해싱을 "어떻게" 하느냐까지가 보안이다.
- **출처**: Krebs on Security (2016.5); arXiv:1703.06586 "The Cryptographic Implications of the LinkedIn Data Breach"

## Part 4. 규모의 전쟁 — 동시접속 1만에서 서버리스까지

### [1999] C10K — 문제에 이름이 붙다

- **문제 제기**: 댄 케걸(Dan Kegel)이 1999년 "C10K 문제" 명명 — 서버 한 대가 동시접속 1만(Connection 10,000)을 감당할 수 있는가.
- **당시 방식의 한계**: 접속 1건 = 스레드/프로세스 1개 방식은 접속자가 늘수록 메모리와 문맥 교환(작업을 번갈아 바꾸는 데 드는 관리 비용)이 폭증했다.
- **출처**: Dan Kegel, "The C10K problem" (kegel.com/c10k.html, 1999)

### 📦 심화 3: 비동기·논블로킹 — 기다리는 동안 다른 일을 한다

서버가 느려지고 다운되는 근본 이유: 요청을 1:1로 붙잡고 순차 처리하면, 느린 작업(디스크 읽기, DB 조회, 외부 API 호출) 하나가 뒤의 모든 요청을 기다리게 만든다.

- **동기(Synchronous)**: 한 요청이 끝날 때까지 다음 요청은 대기.
- **비동기(Asynchronous)**: 기다리는 동안 다른 요청을 먼저 처리.
- **논블로킹(Non-blocking)**: 하나가 막혀도 다른 것들이 계속 진행.

이를 구현하는 두 가지 방식:

| 방식 | 원리 | 비유 | 비용 |
|---|---|---|---|
| **멀티스레드** | 요청마다 작업 흐름(스레드)을 하나씩 배정 | 손님마다 전담 직원을 붙이는 가게 | 직원(스레드)마다 자리·월급(메모리·전환 비용) — 1만 명이면 한계 |
| **이벤트 루프** | 한 흐름이 접수만 하고, 오래 걸리는 일은 맡겨둔 뒤 완료 알림을 받으면 이어서 처리 | 유능한 직원 1명이 주문만 받고 조리는 주방에 맡김 | 직원 1명 비용으로 수만 명 응대 — 단, 그 1명이 직접 오래 계산하면 전체가 멈춤 |

### [2009] Node.js — 한 명의 웨이터가 만 개의 테이블을 받다

- **문제**: C10K — 스레드 모델의 구조적 한계.
- **해결**: 라이언 달(Ryan Dahl)이 2009년 11월 JSConf EU(베를린, 청중 150명)에서 Node.js 발표 — 이벤트 루프 + 논블로킹 I/O를 기본값으로 삼은 서버 런타임. 콘퍼런스 사상 처음으로 기립박수가 나왔다.
- **원리(비유)**: 기존 방식은 테이블마다 전담 웨이터(스레드)를 붙이는 식당. Node는 웨이터 한 명이 주문만 받고 주방(I/O)에 넘긴 뒤 바로 다음 테이블로 이동 — 요리가 끝나면 알림(이벤트)을 받고 서빙한다. 웨이터가 한 명이라도 "기다리는 시간"이 없어 만 테이블을 감당한다.
- **보너스**: 프론트엔드와 백엔드가 같은 언어(JS)가 되면서 풀스택 개발자 시대가 열렸다. [2010.5] Express.js(TJ 홀로웨이척)가 Node 서버 작성을 표준화.
- **실전 증명**: 페이팔이 2013년 주력 페이지를 Java에서 Node로 재작성 — 응답 시간 35% 단축, 코드 33% 감소, 초당 처리량 2배(페이팔 기술 블로그 자체 측정 — 단일 사례임에 유의).
- **새로운 문제**: 콜백 지옥(이후 Promise·async/await로 해결), CPU 집약 계산에는 부적합("웨이터 1명"이 직접 요리하면 홀 전체가 멈춘다).
- **출처**: Ryan Dahl, JSConf EU 2009 발표; PayPal Engineering Blog "Node.js at PayPal" (2013)

### 📦 심화 4: 수직 확장 vs 수평 확장 — "서버를 키우지 말고 늘려라"

사용자가 포화 상태에 이르렀을 때의 두 갈래:

| 방식 | 내용 | 비유 | 한계 |
|---|---|---|---|
| **수직 확장(Scale-up)** | 더 좋은 사양의 서버로 교체 | 더 큰 트럭 한 대로 교체 | 성능엔 물리적 상한이 있고, 2배 성능은 2배보다 훨씬 비싸다. 교체하는 동안 멈춘다 |
| **수평 확장(Scale-out)** | 같은 서버를 여러 대로 늘림 | 트럭을 여러 대로 | 요청을 나눠줄 교통정리가 필요 |

- **로드 밸런서(Load Balancer)**: 들어온 요청을 여러 서버에 골고루 분산시키는 배차 담당자.
- **왜 "늘려라"가 현대 백엔드의 핵심 발상인가**: ① 한 대의 성능에는 상한이 있지만 대수에는 사실상 상한이 없다(비용도 대수에 비례해 선형적 — 괴물 서버 한 대보다 싸다). ② 한 대는 곧 단일 장애점(그 하나가 죽으면 전체가 죽는 지점)이지만, 여러 대면 한 대가 죽어도 서비스는 계속된다. ③ 트래픽에 따라 늘렸다 줄였다 할 수 있다(탄력성 — 클라우드 시대의 전제).
- **연쇄 확인**: 단, 수평 확장에는 전제가 있다 — **어느 서버가 요청을 받아도 상관없으려면 서버가 상태를 기억하지 말아야 한다.** 세션(서버 메모리 저장)이 JWT(사용자 소지)로 진화한 진짜 이유가 바로 이것이다. Part 3의 상태 관리 연쇄와 Part 4의 확장 연쇄는 같은 이야기의 양면이다.
- **실전 사례**: 2022년 11월 티켓마스터가 테일러 스위프트 티켓 판매에서 35억 건 요청을 맞고 마비 — "수요는 언제든 설계 용량을 뛰어넘을 수 있다"는 것을 보여준 현대적 교훈(→ 편성표 9편).
- **캐시·CDN 예고**: 확장의 또 다른 축 — 자주 찾는 데이터를 빠른 메모리에 올려두는 캐시(Redis), 파일을 전 세계에 복사해두는 CDN — 은 **→ 03 데이터베이스편**에서 다룬다.

### [~2014] 마이크로서비스 — 모놀리스를 쪼개다

- **문제**: 모놀리스(한 덩어리 앱)는 ① 한 줄 수정에도 전체 재배포 ② 결제 기능에 문제가 생기면 로그인까지 같이 다운(한 코드 덩어리이므로) ③ 일부 기능만 폭주해도 전체 확장 필요 ④ 수백 명 개발자가 한 코드베이스에서 충돌.
- **선행 사례 [2002경]**: 아마존의 "베조스 API 명령" — 모든 팀은 기능을 반드시 API로만 제공하라는 사내 지침 (출처: 전 아마존 개발자 스티브 예기의 2011년 회고 — **1차 사료가 아닌 회고 기반**임에 유의).
- **명명 [2014.3]**: 마틴 파울러 & 제임스 루이스의 "Microservices" 아티클(martinfowler.com, 2014.3.25)로 개념 대중화. Netflix가 대표 실전 사례.
- **원리**: 거대한 백화점 하나 → 전문 상점가. 기능별(로그인, 결제, 장바구니…)로 서버를 나눠 독립적으로 개발·배포·확장.
- **부속 기술**: API Gateway — 서비스가 여러 개로 나뉘었을 때 사용자 요청이 어디로 가야 할지 정리해주는 정문 안내소(모든 요청이 여기로 들어온다). 서비스끼리는 메시지 큐(요청을 우체통에 넣어두면 상대가 나중에 꺼내 처리하는 방식)로 통신하기도 한다.
- **새로운 문제**: 분산 시스템 복잡도의 폭발 — 서비스 간 통신, 장애 전파, 그리고 "수십 개 서비스를 어떻게 배포·관리하나". 이 문제의 해결책(Docker 2013, Kubernetes 2014, CI/CD)은 **→ 05 배포편**의 주인공이다.
- **균형 감각**: 2023년 아마존 프라임 비디오의 한 팀은 마이크로서비스를 다시 모놀리스로 합쳐 비용을 90% 절감했다(모니터링 서비스 한정). 쪼개는 게 항상 답은 아니다 — **규모와 필요가 답을 정한다.**
- **출처**: Fowler & Lewis, "Microservices" (martinfowler.com, 2014.3); Steve Yegge, "Google Platforms Rant" (2011); Prime Video Tech Blog (2023.3)

### [2014] 서버리스 — 서버 관리라는 일 자체를 없애다

- **문제**: 마이크로서비스로 서비스가 수십 개가 되자, 각각의 서버 준비·확장·패치 관리 부담이 역으로 폭증했다.
- **해결**: AWS Lambda 출시 (re:Invent, 2014.11.13) — 함수 코드만 올리면 요청이 올 때만 실행되고, 실행된 시간만큼만 과금 (FaaS: Function as a Service).
- **비유**: 자가용(자체 서버) → 택시(클라우드 VM) → 호출형 킥보드(서버리스): 탈 때만 쓰고 관리는 아예 남의 일.
- **새로운 문제**: 콜드 스타트(첫 호출 지연), 벤더 종속(특정 클라우드에 묶임), 긴 작업에 부적합.
- **출처**: AWS re:Invent 2014 Lambda 발표

## Part 5. 언어 생태계 — 결국 무엇을 써야 하나

백엔드 언어·프레임워크의 지형도. 각각이 "어떤 필요"에서 태어나 어떤 자리를 차지했는지:

| 진영 | 태생과 자리 |
|---|---|
| **Java + Spring** | 2000년대 초부터 금융권·관공서 등 엔터프라이즈(대기업·기관) 시장의 표준. 수십 년 검증에서 오는 안정성·신뢰가 무기. Spring(1.0, 2004.3)은 Java를 웹 서버 개발에 최적화한 프레임워크 |
| **C# + ASP.NET** | 마이크로소프트가 만든 언어와 프레임워크. 윈도우/MS 인프라를 쓰는 기업 생태계에 최적화 |
| **Go** | 구글이 만든 언어. 가볍고 빠르고 동시 요청 수천 건 처리에 특화 — 복잡한 문법 없이 성능이 나와, 대규모 트래픽을 다루는 서버 인프라(Docker·Kubernetes도 Go로 작성)에서 활용 |
| **JavaScript + Node.js + Nest.js** | 특이 케이스 — 원래 브라우저 전용 언어였으나 2009년 Node.js로 서버 진출. 프론트엔드 개발자가 같은 언어로 백엔드까지 작성. Express가 표준을 만들었고, Nest.js는 더 구조적인 서버 설계(Spring 스타일)를 JS 세계로 가져왔다 |
| **Python + Django/FastAPI** | 읽기 쉬운 문법으로 빠른 개발. Django(2005)가 풀세트를, FastAPI(2018)가 API 특화·AI 서빙을 담당 |

- **그래서 뭘 써야 하나?** — 정답은 없고, **필요가 결정한다.** 고객이 누구인가(금융권이면 Java 생태계가 이미 표준), 서비스 규모(초당 수만 요청이면 Go 같은 선택지), 얼마나 빨리 만들어야 하는가(혼자 빠르게면 Rails/Django/FastAPI), 팀이 이미 아는 언어가 무엇인가.
- **언어들의 본질**: 이름과 문법이 달라도 **하는 일은 동일하다 — HTTP 요청을 받아, 처리하고, 응답을 돌려준다.** 30년간 언어는 바뀌었지만 이 한 문장은 바뀐 적이 없다. 하나의 언어로 이 흐름을 이해하면 나머지는 방언이다.

## Part 6. 결론 — 백엔드의 재정의, 그리고 AI 서빙으로

### 30년의 한 줄 요약

| 시대 | 서버의 정체 |
|---|---|
| 1991 | 파일 배달부 (정적) |
| 1993~2004 | HTML 제조기 (CGI → PHP → 프레임워크) |
| 2005~ | API 창구 (AJAX 이후 — 데이터만 제공, 화면은 프론트엔드 책임) |
| 2014~ | 분산 시스템의 조율자 (마이크로서비스·서버리스) |
| 현재 | 모델 서빙 플랫폼 — AI 시대의 백엔드 |

### [2018~] FastAPI와 AI 서빙 — 이 시리즈의 합류 지점

- **문제**: Python은 AI의 언어가 됐지만, 기존 Python 웹 프레임워크(Django/Flask)는 API 전용으로 쓰기에 무겁거나 느렸고 문서화가 수작업이었다.
- **해결**: 세바스티안 라미레스가 FastAPI 공개 (2018.12) — 비동기(async) 기반 고성능 + 코드에서 API 문서 자동 생성 + 타입 힌트 기반 검증.
- **현재**: Stack Overflow 2025 설문 사용률 15.1%로 Python 웹 프레임워크 중 Flask를 처음 추월. 학습된 AI 모델을 세상에 서비스하는 표준 통로가 됐다.
- **의미**: "모델을 만드는 것"(07 딥러닝)과 "모델을 제공하는 것"(02 백엔드)이 만나는 지점이며, LLM 에이전트(08)도 결국 API를 호출하고 API로 호출당하는 백엔드 위에서 산다.
- **출처**: fastapi.tiangolo.com; Stack Overflow Developer Survey 2025

### 프론트엔드 편과의 연결

- 01편의 결말: "프론트엔드는 백엔드의 API를 호출해 데이터를 받아 화면을 그린다."
- 02편의 결말: "백엔드는 화면을 버리고 API 창구가 되었다."
- 두 문서는 같은 사건(AJAX~SPA 전환)을 반대편 참호에서 본 기록이다. 한쪽만 읽으면 반쪽 역사다.
