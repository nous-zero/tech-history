## Part 1. 토대 — 인터넷과 웹의 등장

### [1969] ARPANET — 인터넷의 첫걸음

- **문제**: 미·소 냉전 중, 핵 공격 등으로 중앙 집중식 통신망이 마비되면 국가 통신 전체가 붕괴할 위험. 중앙 서버 없이 정보를 분산 전송할 네트워크가 필요했다.
- **해결**: 미 국방부 ARPA가 패킷 교환 방식의 ARPANET 구축. **1969년 10월 29일**, UCLA에서 스탠퍼드 연구소(SRI)로 첫 메시지 "LOGIN" 전송 시도.
- **원리**: 데이터를 패킷으로 쪼개 분산 경로로 전송 — 일부 경로가 끊겨도 통신이 유지된다.
- **디테일**: 첫 전송에서 "LO"까지 보낸 뒤 시스템이 다운됐다. 인터넷의 첫 메시지는 사실상 "LO"였다.
- **새로운 문제**: 각 기관이 서로 다른 방식의 네트워크를 쓰면서 상호 연결이 불가능했다.
- **출처**: Leiner et al., "Brief History of the Internet", Internet Society (internetsociety.org)

### [1974 → 1983] TCP/IP — 네트워크의 공통 언어

- **문제**: 서로 다른 종류의 네트워크들이 하나로 연결될 수 없었다.
- **해결**: 빈트 서프(Vint Cerf)와 로버트 칸(Robert Kahn)이 **1974년** TCP 논문 발표. **1983년 1월 1일** ARPANET이 TCP/IP로 공식 전환 ("flag day").
- **원리**: 네트워크 독립성 + 표준화된 언어 + 계층적 구조. 어떤 물리망 위에서든 같은 규약으로 통신한다.
- **현재**: 지금도 인터넷의 근간. 인터넷 = 데이터가 이동하는 물리적 통로(도로망).
- **출처**: Cerf & Kahn, "A Protocol for Packet Network Intercommunication" (1974, IEEE)

### [1989 → 1991] Web — 문서 공유 시스템

- **문제**: CERN에서 연구 자료가 컴퓨터·시스템마다 제각각이라 공유가 안 됐다. "왜 문서 공유가 안 될까?"
- **해결**: **1989년** 팀 버너스리(Tim Berners-Lee)가 Hypertext / **Hyperlink** 개념 기반의 Web을 제안, **1991년** 공개.
- **원리**: 세 가지 발명의 조합.
  - **HTML** (HyperText Markup Language): 문서 구조 정의 언어 (제목·문단·링크)
  - **URL** (Uniform Resource Locator): 문서의 고유 주소
  - **HTTP** (HyperText Transfer Protocol): 문서를 주고받는 규약
- **비유**: 인터넷이 도로망이라면, 웹은 그 위의 우편 시스템 — URL 주소에 따라 문서를 배달한다.
- **새로운 문제**: 초기 브라우저는 텍스트만 표시 가능. 정적인 문서 형태에 머물렀다.
- **출처**: CERN, "A short history of the Web" (home.cern); W3C, "History of the Web"

## Part 2. 브라우저 — 웹의 시각화와 전쟁

> **브라우저의 본질**: 문서를 받아와서 화면에 그려주는 것. 1991년부터 지금까지 변하지 않았다.

### [1993] Mosaic — 그림이 보이는 브라우저

- **문제**: 브라우저에 그림·사진이 표시되지 않았다.
- **해결**: 일리노이 대학교 NCSA(국립 슈퍼컴퓨팅 응용연구소)의 시급 알바생 마크 앤드리슨(Marc Andreessen)과 에릭 비나(Eric Bina)가 텍스트+이미지 브라우저 Mosaic 개발.
- **의미**: 이미지가 본문에 함께 표시되는 최초의 대중적 브라우저 — 웹 대중화의 방아쇠.
- **출처**: NCSA Mosaic 공식 기록 (ncsa.illinois.edu)

### [1994] Netscape Navigator — 브라우저의 상업화

- **문제**: Mosaic으로 폭발적 시장 수요를 확인했으나, 대학 소속 프로젝트로는 한계.
- **해결**: 앤드리슨이 실리콘밸리로 가 짐 클라크와 창업, 완전히 새로운 코드로 Netscape Navigator 출시.
- **결과**: 출시 후 수개월 만에 시장을 장악, 최고 약 70~80% 점유율 (수치는 조사기관별 상이 — 단정 표현 주의).
- **출처**: Computer History Museum, "Netscape Navigator" 아카이브

### [1995] JavaScript — 웹이 반응하기 시작하다

- **문제**: 웹을 클릭해도 아무 반응이 없었다. 모든 동작이 서버 왕복을 요구했다.
- **해결**: 넷스케이프의 브렌던 아이크(Brendan Eich)가 **10일 만에** 브라우저 전용 프로그래밍 언어 개발.
- **원리**: 브라우저 안에 JS 엔진이 내장되어 코드가 실행된다.
  - 이벤트 발생 → 신호 접수 → **DOM**(Document Object **Model**) 조작
  - 브라우저는 HTML을 읽는 순간 페이지의 모든 요소를 지도처럼 저장(DOM 트리)하고, JS가 이 지도를 보며 원하는 요소의 글자·색을 바꾼다.
  - 결과: 팝업, 실시간 입력 검증, 화면 일부 변경이 가능해졌다.
- **이름의 유래**: Mocha → LiveScript → **JavaScript**. 당시 인기 절정이던 Sun의 Java 마케팅에 편승한 개명. **Java와 JavaScript는 이름만 비슷한 다른 언어다.**
- **출처**: Brendan Eich 본인 회고 (brendaneich.com); JavaScript 20주년 기록 "JavaScript: The First 20 Years" (ACM HOPL IV, 2020)

### [1995.8] Internet Explorer — 1차 브라우저 전쟁 (무기: 끼워팔기)

- **경위**: Microsoft가 Spyglass사를 통해 NCSA Mosaic 코드를 라이선스받아 IE 개발. (직접 구매가 아니라 **재라이선스** — 이후 로열티 분쟁 소송까지 있었다.)
- **전략**: Windows 95에 IE를 기본 탑재하는 끼워팔기로 시장 장악 (1995~2001, 이후 미국 반독점 소송의 핵심 쟁점).
- **결과**:
  - 넷스케이프 패배 → **1998년** 소스 코드 공개 → Mozilla 프로젝트 → 훗날 Firefox(2004)로 부활.
  - 양사가 자기 브라우저에서만 작동하는 기능을 경쟁적으로 추가 → **같은 코드가 브라우저마다 다르게 보이는** 크로스 브라우저 문제 발생.
- **출처**: United States v. Microsoft Corp. (2001) 판결 기록; Mozilla 프로젝트 연혁 (mozilla.org)

### [1996] CSS — 뼈대와 옷의 분리

- **문제**: 정적 페이지를 꾸미느라 HTML에 직접 스타일을 섞어 쓰면서, 문서 구조와 시각 스타일이 뒤엉켜 코드가 엉망이 됐다.
- **해결**: W3C가 CSS1(Cascading Style Sheets) 표준 발표. 제안자는 호콘 비움 리(Håkon Wium Lie).
- **원리**: **HTML은 뼈대, CSS는 옷** — 구조와 표현의 분리. Cascading = 스타일이 위에서 아래로 적용/상속된다.
- **완성**: 이로써 웹 화면의 3대 요소 **HTML(구조) + CSS(표현) + JavaScript(동작)** 조합이 완성됐다. 이 셋은 30년이 지난 지금도 웹의 근간이다.
- **새로운 문제**: 브라우저마다 CSS 렌더링이 제각각 — 크로스 브라우저 지옥의 심화.
- **출처**: W3C CSS1 Recommendation (1996.12, w3.org)

### 📦 심화: 브라우저 렌더링 파이프라인

```
URL 입력 → 브라우저
  1. Parsing     : HTML/CSS를 읽어 페이지 요소 전체 파악
  2. Render Tree : 화면에 실제로 보여줄 것만 추리기
  3. Layout      : 각 요소의 위치·크기 계산
  4. Paint       : 색·이미지를 칠해 시각화
```

- **Reflow(리플로우)**: JS로 DOM을 수정하면 Layout 계산을 다시 해야 한다. 리플로우가 잦으면 성능이 급락한다.
- **프론트엔드 최적화의 핵심 = 리플로우를 얼마나 줄이는가.**
- **출처**: Google web.dev, "Rendering performance"

### [2004~2008] 2차 브라우저 전쟁 (무기: 속도) — Chrome 승리

- **문제**: 독점에 안주한 IE의 정체된 업데이트, 웹 표준 미준수로 개발자·기업의 원성 누적.
- **1차 공격 [2004]**: 넷스케이프의 유산 Firefox가 IE 점유율을 잠식하기 시작.
- **결정타 [2008]**: Google Chrome 등장. 핵심 무기는 **V8 JavaScript 엔진**.
  - 이전 방식: 코드를 한 줄씩 해석(인터프리터)
  - V8: 코드를 통째로 기계어로 미리 컴파일(JIT) → JS 실행 속도 수십 배 향상
- **결과**: 출시 4년 만인 2012년 IE 추월(StatCounter 기준), 현재 점유율 60%+. IE는 2022년 6월 공식 지원 종료.
- **역사적 의미**: V8의 속도 혁명이 다음 시대(Node.js, 나아가 오늘날 AI 코딩 도구 생태계)의 토대가 됐다.
- **출처**: StatCounter Global Stats; Microsoft IE 지원 종료 공지 (2022.6.15)

## Part 3. 프론트엔드의 4단계 전환

### 전환 ① 화면 꾸미기 → 프로그래밍 [2006~2009]

#### [2006] jQuery — DOM 통역사

- **문제**: 브라우저마다 DOM 조작 방법이 달라, 같은 기능을 브라우저별로 따로 코딩해야 했다.
- **해결**: 존 레식(John Resig)이 jQuery 공개. 브라우저별 차이를 하나의 문법으로 통일.
- **원리**: 라이브러리 = **반찬가게** — 필요한 반찬(기능)만 사다 쓴다.
- **효과**: 크로스 브라우저 문제 대부분 해소 + 코드 길이 대폭 단축.
- **새로운 문제**: 웹이 커지고 복잡해지자 JS 코드가 폭발적으로 늘었고, 대규모 애플리케이션에서는 코드 관리가 붕괴(버그, 중복, 스파게티화).
- **출처**: jquery.com 공식 연혁

#### [2009] Node.js — JS의 탈옥

- **문제**: V8의 압도적 속도를 본 개발자들이 "이 엔진을 브라우저 밖에서 쓸 수 없을까?" 고민하기 시작.
- **해결**: 라이언 달(Ryan Dahl)이 Chrome의 V8 엔진을 추출해, 브라우저 없이 JS를 실행하는 **런타임** Node.js 개발.
- **원리**: 런타임 = 코드가 실제로 돌아가는 플레이어. 이전에는 브라우저라는 런타임밖에 없었으나, 이제 터미널·서버 어디서든 JS가 돌아간다.
- **의미**: JS가 "브라우저 전용 언어"에서 "무엇이든 할 수 있는 언어"로 변신. 프론트엔드 개발자가 서버까지 넘볼 수 있게 된 분기점.
- **출처**: Ryan Dahl, JSConf EU 2009 발표 영상

### 전환 ② 맨땅 헤딩 → 레고 조립 [2010~2011]

#### [2010] npm — 프로그래밍 세계의 앱스토어

- **문제**: 라이브러리가 폭증하면서, 흩어진 코드를 어떻게 버전 관리하고 공유할 것인가의 문제 발생.
- **해결**: npm(Node Package Manager) 등장. 전 세계 개발자의 라이브러리가 등록되는 중앙 저장소.
- **원리**:
  - `npm install react` 한 줄이면 설치 완료.
  - **package.json** = 프로젝트 명세서 — 어느 컴퓨터에서든 동일한 환경 재현.
  - **dependency(의존성)**: 라이브러리 간 복잡한 의존 관계를 npm이 자동 관리.
- **산업적 의미**: 직접 코드 작성(맨땅 헤딩) → npm에서 가져다 조립(레고 조립식)으로 개발 방식 자체가 전환. 오늘날 AI 코딩도 이 조립식 생태계 위에서 작동한다.
- **출처**: npmjs.com 공식 문서

#### [2011] Bootstrap — 디자인의 밀키트

- **문제**: 조립식 산업이 되었는데도 디자인만은 매번 CSS를 수작업으로 코딩해야 했다.
- **해결**: 트위터 개발자들이 사내 도구를 오픈소스로 공개 — CSS **프레임워크**의 대중화.
- **원리**: 프레임워크 = **밀키트** — 재료와 요리 순서가 모두 정해져 있다. (라이브러리=반찬가게와 대비)
- **새로운 문제 [~2017]**: 모두가 같은 밀키트를 쓰니 **웹사이트들이 전부 비슷하게 생기는** 획일화 발생.
- **출처**: getbootstrap.com; Mark Otto 개발 회고

#### [2017] Tailwind CSS — 다시 조립의 자유로

- **문제**: Bootstrap발 디자인 획일화.
- **해결**: 유틸리티 클래스 조합으로 디자인 세부 사항을 직접 조정하는 Tailwind CSS 등장 (Adam Wathan).
- **원리**: 완성된 밀키트가 아니라, 잘게 쪼갠 레고 블록의 조합.
- **참고**: AI가 생성하는 웹 디자인이 서로 비슷해 보이는 현상에도 특정 프레임워크 스타일 학습의 영향이 있다. *(← 이 문장은 경험적 관찰이며 정량 출처 없음 — 콘텐츠화 시 "개인적 관찰" 표기 권장)*
- **출처**: tailwindcss.com; Adam Wathan, "CSS Utility Classes and Separation of Concerns" (2017)

### 전환 ③ 수동 갱신 → 자동 반응 [2013~]

#### [2013] React — 데이터가 바뀌면 화면은 알아서 바뀐다

- **문제**: jQuery의 한계 — 이벤트·상태가 변할 때마다 화면 갱신을 개발자가 일일이 코딩해야 했다. 상태가 늘수록 갱신 코드가 기하급수로 복잡해졌다.
- **해결**: 페이스북이 React 공개.
- **3대 개념**:
  1. **추상화(Abstraction)**: 복잡한 동작은 숨기고 간단한 명령만 노출
  2. **컴포넌트(재사용성)**: 한 번 잘 만든 UI 조각을 재사용
  3. **상태 관리(State)**: 앱이 기억해야 할 모든 정보를 상태로 관리 — 상태가 바뀌면 화면은 React가 알아서 갱신
- **패러다임 전환**: 개발자는 데이터(상태) 관리에 집중, 화면 업데이트는 프레임워크의 책임으로 이관.
- **출처**: React 공식 블로그, "Why did we build React?" (2013)

#### 심화: BUILD — 우리가 쓰는 코드 ≠ 서비스에 올라가는 코드

- **문제**: ① 최신 JS 문법을 구형 브라우저가 이해 못 함. ② 프로젝트 파일이 수백 개로 쪼개져, 브라우저가 하나씩 요청하면 속도가 급락.
- **해결**: 빌드(BUILD) 단계의 등장. 도구: **Webpack, Vite** 등.
  1. **트랜스파일링**: 최신 코드 → 구버전 브라우저용으로 자동 번역
  2. **번들링**: 흩어진 수백 개 파일을 몇 개로 묶기
  3. **트리셰이킹**: 설치한 패키지 중 실제로 쓰지 않는 코드를 자동으로 솎아내기
  4. **프로덕션 최적화**: 불필요한 내용 제거·압축 (결과물은 사람이 읽을 수 없는 형태)
- **출처**: webpack.js.org; vitejs.dev

### 전환 ④ 웹 → 앱처럼 [2010s~현재]

#### SPA — Single Page Application

- **문제**: 기존 **MPA**(Multi-Page Application)는 페이지마다 별도 HTML이 존재 → 이동할 때마다 서버에서 새 HTML을 받아 전체 새로고침 → 흰 화면 깜빡임. 모바일 앱처럼 매끄러운 전환을 사용자들이 요구.
- **해결**: SPA — HTML 파일은 하나, 첫 접속 때 JS를 모두 받아온 뒤 **클라이언트 사이드 라우팅**으로 JS가 화면만 교체.
- **효과**: 빠른 전환, 상태 유지, 앱 수준의 UX.
- **새로운 문제**: **SPA는 UX를 얻고 SEO를 잃었다.** 검색엔진 크롤러가 빈 HTML만 보게 됨 + 초기 로딩 시간 증가.

#### SSR vs CSR — 그리고 하이브리드

| 방식 | 원리 | 얻는 것 | 잃는 것 |
|---|---|---|---|
| **CSR** (Client-Side Rendering) | JS가 브라우저에서 화면을 그림 (SPA 방식) | 빠른 전환, 앱 같은 UX | SEO, 초기 로딩 |
| **SSR** (Server-Side Rendering) | 서버가 완성된 HTML을 미리 만들어 전송 | SEO, 빠른 첫 화면 | 서버 부하 증가 |
| **하이브리드** | 상황별로 SSR/CSR 혼용 (대표: **Next.js**) | 양쪽 장점 절충 | 구조 복잡도 |

- **하이드레이션(Hydration)**: SSR로 받은 정적 HTML에 JS를 심어 인터랙티브하게 만드는 과정 — "마른 HTML에 물을 부어 살아있는 앱으로."
- **OG 태그**: 카카오톡·슬랙에 URL을 붙이면 뜨는 미리보기(Open Graph). 제목·설명·이미지를 HTML 헤더에 정의하며, 크롤러가 읽어야 하므로 SSR 환경에서 안정적으로 동작.
- **연쇄의 법칙 재확인**: SPA는 UX를 얻고 SEO를 잃었다 → SSR은 SEO를 얻고 서버 부하를 얻었다. **모든 해결은 새로운 문제를 낳는다.**
- **출처**: Next.js 공식 문서 (nextjs.org/docs); Google Search Central, "JavaScript SEO basics"

## Part 4. 결론 — 프론트엔드 직군의 재정의

### 더 이상 "디자인"이 아니다

| 시대 | 역할 분담 |
|---|---|
| 과거 | **웹 퍼블리셔**가 HTML/CSS로 화면 모양을 잡고 → 백엔드 개발자가 조립. 서버가 HTML을 직접 만들어 내려주는 구조 |
| SPA 이후 | **프론트엔드 개발자**가 React 등으로 복잡한 UI 로직을 짜고, 백엔드의 **API**를 호출해 데이터를 받아, 그 데이터로 화면을 그리는 전 과정을 책임 |

- **API** (Application Programming Interface) = 백엔드가 제공하는 창구.
- **현재의 프론트엔드**: UI 아키텍처 설계 + 상태 관리 + 성능 최적화(리플로우 최소화) + API 통신을 담당하는 **독립적 엔지니어링 영역**.

### 학습 순서에 대한 답

> Q. "프론트엔드 → 백엔드 → DB → 웹서버 → 배포 → 모바일 → AI" 순서가 맞는가?

- **역사 순서**: 웹서버·백엔드가 먼저다 (초기엔 서버가 HTML을 직접 만들어 내려줬으므로).
- **학습 순서**: 눈에 보이는 프론트엔드부터 시작하는 현재의 표준 커리큘럼이 합리적이다.
- **결론**: 역사 순서 ≠ 학습 순서. 두 축을 분리해서 인식할 것.
